# CLAUDE.md

Guidance for working in `data-preprocessor/`. The repo-wide overview is in the root `CLAUDE.md`.

### Output JSON-LD contract

Both output files must match what `hra-ftu-ui` expects (see full examples in `ftu2-pseudo-code.md`):
- `ftu-cell-summaries.jsonld`: `@graph` of `CellSummary` objects keyed by `cell_source` (a dataset DOI or entity URL fragment), each with a `summary` array of `CellSummaryRow` (`cell_id`, `cell_label`, `genes[]` with `ensemble_id`/`gene_id`/`gene_label`/`mean_expression`).
- `ftu-datasets.jsonld`: `@graph` of `FtuIllustration` objects (`@id` = `https://purl.humanatlas.io/2d-ftu/<organ>-<ftu>`) each with `data_sources[]` (`Dataset` with label/link/description/year/authors). hra-ui maps a data source's `@id`→Dataset ID, `label`→Dataset Title, `link`→Publication DOI, `description`→Publication Title and `year`→Year, and `filterSummaries` matches `@id` against `cell_source`, so `@id` must stay `<dataset_id>#CellSummary_<ftu suffix>` in both files. Script 40 also writes `cell_type_annotation_tool`, `sex`, `age`, `bmi` and `ethnicity`, which hra-ui's `toSourceReferences` shows in the Cell Type, Sex, Age, BMI and Ethnicity columns. It also writes `health_status` (Health Status column). Neither metadata CSV has a health or disease column, so it's set per source in `CELL_SUMMARY_SOURCES` and added as a column by `load_dataset_metadata`. HRApop is `Healthy`. For the anatomogram, `health_status_by_dataset` points at `anatomogram-data/anatomogram-health-status-output.json` (`[{dataset_id, donor_disease}]`, first letter capitalized on load, e.g. `Healthy`, `Type II diabetes mellitus`); datasets missing from it are `TBD`. That file was made once by `data-preprocessor/scratch/fetch-anatomogram-health-status.py` from per-dataset `dataset.json` files downloaded from the hra-workflows-runner data repo with `scratch/download-dataset-json.sh`; neither script is part of the pipeline run. `dataset_id`, `dataset_link` and `development_stage` are written but not shown. hra-ui's zod schema makes these fields optional, not nullable: never write `null`, or the whole file fails validation. `sex`, `age`, `bmi` and `ethnicity` are written as `"None"` when missing (`UNKNOWN_WHEN_MISSING`); other fields are left out when they have no value. `age` is a number, or a range string like `"60-69"` for CxG's HsapDv decade stages (the Nth decade is (N-1)*10 to (N-1)*10+9). hra-ui accepts `number | string` for `age` and `bmi` (hubmapconsortium/hra-ui#2334, #2335). Any value that fails its schema makes the whole file fail validation, which empties both the datasets and the cell type/biomarker tables, so check the deployed `wc.js` schema before pushing a new field type. Publication title/year/authors come from Crossref, cached in `raw-data/` (`DOI_METADATA_CACHE`). Some CellxGene collections have no DOI in HRApop (neither the metadata CSV nor `sankey.csv`). Add those to `DOI_OVERRIDES` in `config.yaml` (collection ID → DOI); it's only applied where `publication` is empty. HuBMAP datasets have no DOI in the metadata CSV either. Where `publication` is still empty, `apply_hubmap_publications` looks it up in HuBMAP's public search API (`HUBMAP_SEARCH_API`). The entity API's `descendants` endpoint needs a login, so it isn't used. HuBMAP `Publication` entities list the datasets they used as ancestors. A candidate is a publication that lists the dataset itself or one of its raw (parent, `entity_type == "Dataset"`) ancestors. Donor and sample ancestors aren't counted, so a paper isn't picked just because it used another dataset from the same donor. The candidate with the fewest linked datasets wins, so e.g. the kidney papilla atlas beats the whole-kidney atlas. `HUBMAP_EXCLUDED_PUBLICATION_DOIS` lists papers that are never used as a source: the two HRA papers that reuse the data, and the HuBMAP Data Portal paper. Results are cached per dataset (DOI or `null`) in `raw-data/` (`HUBMAP_PUBLICATIONS_CACHE`); delete the cache to pick up newly registered publications. 

#### Minimum cells per cell type

`iterate_preferred_cell_summaries` (`shared.py`) drops a dataset's cell types that have fewer than `MIN_CELLS_PER_CELL_TYPE` (`config.yaml`, 10) cells. This filter runs after the dataset's annotation tool is picked, so it never changes which tool is used. 40, 41 and 50 all read through this function, so the datasets, cell summaries and reports stay in sync. A dataset whose cell types for an FTU are all dropped disappears from that FTU in both files. Stage 50's `cell_types_under_10_cells_per_ftu.csv` lists everything the rule removes. It's built by `load_cell_counts_without_min_cells_filter`, which reads `iterate_preferred_cell_summaries(min_cells=0)` and rebuilds 40's dataset → FTU mapping, because `ftu_to_datasets.json` no longer has the removed datasets. It has one row per dataset, FTU and cell type. `dataset_removed_from_ftu` is `True` when none of the dataset's cell types for that FTU are left. It also lists cell types with an empty gene list, which 41 used to write; they all have 1 cell.

#### Duplicate datasets across sources

The same donor's data can be in HRApop more than once: in two versions of a CellxGene collection, or in both HuBMAP and CellxGene. Duplicates are dropped by `is_excluded_dataset` in `shared.py`. `iterate_filtered_cell_summaries` and `load_filtered_dataset_metadata` call it, so 40, 41 and 50 all skip them, and stage 20 doesn't need a rerun. The `analysis/general-analysis/` scripts read the HRApop universe directly, so their counts still include these duplicates. There are two lists in `config.yaml`:
- `EXCLUDED_CELLXGENE_COLLECTIONS`: whole collections, by CellxGene collection ID. It holds the kidney atlas ("An atlas of healthy and injured cell states and niches in the human kidney") Version 1.0 (`bcb61471…`, 2022, 78 datasets), because all 59 of its donors are also in Version 1.5 (`0f528c8a…`, 2024, under the same donor IDs). The newer version is kept.
- `EXCLUDED_DATASETS`: single datasets, by full `dataset_id`. It holds 40 HuBMAP UCSD kidney `RNAseq [Salmon]` datasets from 8 donors that are probably also in kidney atlas Version 1.5. CellxGene is kept, because it's the published and newer version: HuBMAP published these between 2021 and 2023, and 12 of them already have a newer HuBMAP revision. How they were picked:
  - HuBMAP doesn't publish lab donor IDs, so donors were matched on sex and exact age; race agrees too (White in HuBMAP, European in CellxGene). This is strong evidence, not proof. Each donor's CellxGene match is in a comment in the list.
  - Only datasets that HuBMAP links to the kidney atlas paper (`10.1038/s41586-023-05769-3`) are listed.
  - HBM295.GHMR.582 and HBM477.DBJN.952 (both male, 54) are kept, because they both match the one CellxGene donor KRP461, so at least one match is wrong.
  - Still open, so kept for now: 14 more UCSD `RNAseq [Salmon]` datasets from the same 8 donors. 8 of them link to the kidney papilla atlas instead (`10.1038/s41467-023-38975-8`), which may be different tissue samples; 6 of HBM984.MHHN.738's link to no paper.
  - The Broad `Slide-seq [Salmon]` datasets (spatial, different cells) and the 2 unmatched UCSD donors (HBM277.DBXJ.256, HBM464.FJWN.992) are kept.

  To redo the matching, compare each HuBMAP donor's sex/age from the search API (`donor.hubmap_id`, `dataset_type`, `group_name`) with the CellxGene donor IDs in `dataset_id` (`#<donor>$<organ>`). FTU exclusivity comes from `load_exclusive_cts_by_ftu()` (the `exclusive_ct_in_ftu` column, same as the analysis script). A CT exclusive to several FTUs of one organ, e.g., the nephron and a loop of Henle inside it, counts for each of them. 40 lists a dataset under an FTU only when 41 writes a cell summary for it (preferred tool, CT exclusive to that FTU, non-empty `gene_expr`), so every table row has expression data.
